Defect (evidenced this session): `beam_trace::RingBuffer::rebase()` in /home/matt/Git/Trexy/crates/beam-trace/src/ring.rs exists precisely so f32 sample timestamps never lose resolution over a session (TRACE-FORMAT.md §5: 'the epoch is rebased per ring-buffer generation ... so precision never degrades'), but its ONLY caller in the workspace is its own unit test. Nothing in the live path calls it, and after ~3.5 hours of uptime a running session reported '0 samples this frame' — at t≈12600 s the f32 ulp is ~1 ms, so microsecond-spaced samples collapse and the strictly-increasing nudges in the producer inflate timestamps ahead of the wall clock. Fix it end to end. The live path is the producer thread in /home/matt/Git/Trexy/crates/tube-shell/src/source.rs (`produce()`, `LiveSource`); the consumer is app.rs, which feeds `source.elapsed()` and `rendered.field.simulated()` into `source.window(from, to)` and `field.advance(...)` — the Field's SubstepClock (crates/tube-renderer/src/substep.rs) also casts substep boundaries to f32, so timestamps must simply never grow large. Suggested design: the producer rebases the ring (new epoch = current absolute session time, generation bump) once ring-relative time passes a threshold chosen so the f32 ulp stays well below the finest emitted sample spacing (e.g. 30–60 s of ring time; ulp at 64 s is ~7.6 µs — justify the choice in a comment); the shell then re-anchors the renderer's clock on a generation change. crates/tube-renderer must NOT be modified — `Field::new` already takes an epoch, `Field::clear` exists, and app.rs already rebuilds the Field (on resize), so reuse those existing paths from the shell side. Nothing else in tube-shell, nothing in tube-renderer, no shader changes.
