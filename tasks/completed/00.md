`SubstepClock` in /home/matt/Git/Trexy/crates/tube-renderer/src/substep.rs can be
created at an origin (`new`/`with_dt`) and pushed forward (`skip_to`), but there is no
way to tell an existing clock that its zero has moved. That gap blocks the ring-buffer
rebase the trace format requires (TRACE-FORMAT.md §5), because sample `t` is f32 and
must stay small, while the renderer's clock must agree with it about what "now" means —
so both origins have to move together, and only one of them can currently move at all.

Add `SubstepClock::reorigin(&mut self, origin: f64)`: set `self.origin = origin` and
recompute `self.steps` so that `simulated()` returns the same absolute instant it did
immediately before the call. `origin` and `steps` are already f64/u64 and lose no
resolution at any session length, so this is bookkeeping — do NOT widen anything, and do
NOT change `dt` or the substep grid spacing. `steps` is counted rather than accumulated
precisely so the grid never drifts; keep that property.

Expose it on `Field` (crates/tube-renderer/src/frame.rs) as a thin forwarding method,
e.g. `Field::reorigin(&mut self, origin: f64)` delegating to the clock. It must NOT
touch any texture, buffer or bind group: the phosphor holds deposited energy, not
timestamps, so a clock re-origin is invisible to it. A method that allocates or clears
anything is the wrong implementation — `Field::new` already exists for that and clearing
the phosphor mid-session is the outcome this exists to avoid.

Add unit tests in substep.rs covering: (1) `simulated()` is unchanged (within one `dt`)
across a `reorigin` call; (2) after re-origining, `advance()` continues to emit
boundaries on the same `origin + k·dt` grid relative to the new origin, with no substep
emitted twice and none skipped; (3) re-origining to a later zero and to an earlier one
both behave; (4) the host-independence property still holds — the existing
`the_field_does_not_depend_on_the_host_refresh_rate` style check, that chopping the wall
clock differently cannot change which substeps run, must not regress.

Touch ONLY crates/tube-renderer/src/substep.rs and the forwarding method in
crates/tube-renderer/src/frame.rs. Do not modify any shader, any other renderer file,
fixtures/blessed/*.png, or profiles — a clock method cannot change rendered output, so
nothing needs re-blessing and nothing may be re-blessed. Do not wire it up to anything
yet; task 2 does that.

Verify: `cargo test -p tube-renderer`, then `cargo test --workspace` all green (89 tests
currently pass), and `cargo clippy --workspace --all-targets` with zero warnings. Do not
commit.
